# Review: spec — rework

The direction is viable, but planning is blocked by contradictions in the renderer API, finish-phase ordering, and concurrency model. In particular, the normal retro cannot contain the disposition, and the proposed renderer cannot obtain task titles.

- **blocking** spec.md:88 — The initial retro cannot include the disposition: `decideFinish` emits the retro before asking `branch_finish`, so `state.Disposition` is necessarily nil when the normal skeleton is built. The spec nevertheless requires the disposition to be always rendered, G6 requires it as one of five sources, and line 221 explicitly places changing that ordering out of scope. Decide whether the retro moves after disposition, is regenerated after disposition, or deliberately omits it on the initial pass.
- **blocking** spec.md:77 — The renderer has no access to task titles: `ShippedRow` carries only `Tasks []int`, while `RenderSkeleton` receives only `RetroInputs` and `SkeletonExtras`; neither contains `plan.Index` or an ID-to-title mapping. Therefore it cannot satisfy the requirement, repeated in goals.md G2, to render task IDs and titles from `plan.Index`. Carry titles in each row or pass an explicit immutable lookup into the renderer.
- **blocking** spec.md:167 — Atomic per-file writes do not make the unlocked rewrite concurrency-safe: The command rewrites two tracked files sequentially without a lock. In the archived phase, concurrent `takt next` calls `recommitArchive`, which stages and commits any dirty bundle content, so it can commit after one file is replaced but before the other is written. Purity and per-file atomic renames do not provide a consistent multi-file snapshot. The design needs coordination with archived `next`, a transactional publication strategy, or an explicit prohibition on concurrent mutation.
- **blocking** spec.md:87 — Reasonless gate answers have contradictory rendering rules: The decision-source list includes only `gate_answered` events with a non-empty reason, and goals.md G6 says the same. Line 114 instead says a legacy event is rendered as a choice with no reason. These produce different output for legacy and ordinary reasonless events; specify whether they are omitted or rendered, then align the goals and tests.
- **major** spec.md:68 — Assumptions have two conflicting ownership paths: `SkeletonExtras` separately contains `Assumptions`, but `BuildDecisions(events, state, assumptions)` already filters those assumptions and emits `spec_assumption` decisions. It is unclear whether `RenderSkeleton` consumes `ex.Assumptions`, consumes only `ex.Decisions`, or risks rendering assumptions twice. Remove the redundant field or define a single ownership path.
- **minor** spec.md:189 — Documentation target names the wrong section: The design document's CLI command table is in §5.1, not §6. Section 6 describes the command prompt. goals.md G11 repeats the same incorrect target, so both should identify where the new `takt retro` command is actually documented.
