# Review: spec — rework

The overall approach is plausible, but planning must wait: the timeout envelope is mathematically insufficient, the outer and inner close deadlines contradict the stated strict-containment rule, and one success check cannot pass as written. Backend mapping and several required behaviors also lack testable decisions.

- **blocking** spec.md:42 — The close-wave envelope undercounts verification time: The formula budgets one `defaultVerifyTimeout`, but the code runs every verify command serially for every done task before review (`taskOutcome` calls `wave.RunVerify`, whose loop executes each command sequentially). Plans impose no one-command limit. One task with four commands can consume 40m before up to 30m of review, so the proposed 60m cap can expire. Define a bound based on command/task multiplicity, derive the deadline dynamically, or change the execution model.
- **blocking** spec.md:53 — Equal outer and inner close deadlines violate strict containment: The spec says wrapping deadlines must strictly exceed their worst case, but permits `closeTimeoutS >= closeWaveTimeout` and chooses 60m for both. Startup, cancellation, result serialization, and process-exit overhead mean the session deadline can fire before `takt close-wave` reports its own timeout result. Require and budget a positive outer margin.
- **blocking** goals.md:14 — The documented grep success check is impossible: `grep '"timeout": "5m"' README.md docs/` also searches this run's `docs/takt/lets-work-on-60-and-62/spec.md`, whose line 80 intentionally contains that exact old-value string. The command will still return a match after the target examples are updated. Restrict the check to the two intended documents or use a context-specific assertion.
- **major** spec.md:149 — The proposed envelope test cannot observe all three constants: The test is assigned to `internal/decide`, but `closeWaveTimeout` is an unexported constant in `internal/cli`; the other two constants are also private. The spec must choose a shared/exported deadline representation or split the assertions across packages. As written, one decide test cannot fail when any of the three constants changes.
- **major** spec.md:67 — Deadline rendering is undefined for valid non-shipped reviewer names: `backends.reviewer` is not validated to only `copilot` and `claude`; the registry also contains `fake`, and unknown names are tolerated until selection. `config.Backends` has timeout fields only for copilot and claude, so `backends.fake.timeout` or an unknown backend has no current deadline or real configuration key. Specify whether such entries are omitted, rendered with the literal placeholder, rejected by config validation, or represented through a generalized backend map.
- **major** goals.md:9 — The unset backend fallback is not actually tested: G1 requires the unset-`Timeout` fallback to agree with the shipped default, but its evidence only asserts config defaults and says backend tests pass. The testing section likewise specifies no assertion of `internal/backend/run.go`'s fallback. Add a direct cross-package equality test or expose a single shared default so drift is structurally impossible.
- **major** goals.md:13 — Goals omit the specified git-read error behavior: B2 explicitly requires git read errors to return `git push origin <branch>` without failing the archived stop, but G5 and the testing section cover only ahead, fully pushed, and missing-ref states. Add an injected-error case and corresponding success criterion so goals.md matches the spec.
- **minor** spec.md:122 — Not-an-ancestor does not mean strictly ahead: `IsAncestor(<branch>, origin/<branch>) == false` also covers diverged histories, not only a branch that is ahead. The cleanup may still be appropriate because local commits are absent remotely, but the requirement and documentation should say “contains local commits not present in the remote-tracking ref” or explicitly define divergence behavior.
